# worker

## Purpose

Run durable Pi engineering workers without granting parent authority. A worker is a stable identity with one exact Pi session, fixed provider route, and private writable workspace. A run is an ephemeral asynchronous process that must finish with a typed semantic handoff; process exit alone is not completion.

## Provides

Parent surface:

- `worker_run({ runs: [...] })`
- `worker_control({ action: "status" | "result" | "cancel" | "discard", ... })`
- `worker_review({ workerId, runId, workspaceRepo, focus? })`
- `worker_fold_prepare({ repositories: [...] })`
- `worker_fold_resolve({ request: { kind: "start" | "resume", ... } })`
- `/worker:list [--all]`
- `/worker:status <worker-id>`
- `/worker:view <worker-id> [--stream both|stdout|stderr] [--tail 1..500] [--follow]`
- `/worker:ack <worker-id>`
- `/worker:cancel <worker-id>`
- `/worker:discard <worker-id> --confirm`

Worker-only RPC surface:

- `worker_handoff`
- `worker_task_read`
- `worker_task_update`
- `shell_start`, `shell_status`, `shell_read`, `shell_cancel`

`/worker:list` is provider-free and shows up to 100 active (`queued` or `running`) workers owned by the exact current chat. `/worker:list --all` also includes handed-off, failed, and cancelled workers. Both views report their exact selected count and any omitted rows instead of failing. `/worker:status <worker-id>` shows the full canonical record for one known worker.

The parent owns grounding, assignment acceptance, review, integration, promotion, and task closure.

## Tool schema

```ts
worker_run({
  runs: [
    {
      kind: "new",
      taskIds: string[],
      guidance?: string,
      route?: "provider/model[:thinking]",
      completionDelivery?: "steer" | "followUp",
      initialRepos?: Array<{ source: string; revision?: string }>
    }
    | {
      kind: "resume",
      workerId: string,
      message: string,
      addTaskIds?: string[],
      completionDelivery?: "steer" | "followUp"
    }
  ]
})
```

`runs` accepts 1–8 entries. One durable worker may have at most 32 unique assigned task IDs across its initial run and all resumptions. New workers use `defaultRoute` from `worker-settings.json` unless `route` is explicit. All implementation and integration routes reject `max` thinking and every Claude Fable model rather than clamping or substituting. Persisted legacy routes remain truthfully recorded but cannot resume until a new non-`max`, non-Fable worker is started. The resolved provider, model, and thinking level are returned in the receipt and every status/result surface. Resume cannot change the worker session, workspace, provider, model, or thinking level. `completionDelivery` defaults to `steer`: use `steer` to get results as soon as they are ready, and `followUp` for lower-priority tasks that should be investigated after other work is finished.

```ts
worker_control({
  action: "status" | "result" | "cancel" | "discard",
  workerId?: string,
  confirm?: true
})
```

`status` without a worker ID lists at most 100 workers belonging to the exact parent session; with an ID it returns one canonical summary, including any durable repository-candidate inventory counts and bounded summaries. `result` requires a settled run, validates the persisted worker/run handoff identity and hash-bound repository inventory, returns the typed handoff plus exact bounded candidate details in model-visible content, and atomically marks pending delivery observed only after every persisted result artifact validates. `cancel` uses the same authoritative cleanup path as the user command; because its synchronous tool result already reports settlement, it does not queue a duplicate completion turn. `discard` refuses active/leased workers and requires literal `confirm:true`. Tool-safety deterministically allows every valid `worker_control` action without model or human review, while malformed IDs, missing confirmation, and unsupported fields remain reviewed. Use `shell_read` with returned job IDs for logs rather than duplicating log streaming in `worker_control`.

`worker_review` is the sole independent code-review path. It reviews one exact repository from a completed `ready_for_review` or `assignment_complete` handoff and requires exact parent-session ownership, worker/run/candidate identity, a hash-bound inventory, a clean foldable commit, no active run or lease, and the worker's exact persistent container already stopped. Persistent container identity remains tied to its creation run and is valid across implementation resumptions; review never stops, starts, kills, parks, or replaces it. Read-only Docker inspection verifies the persisted container ID and worker/run/nonce labels before and after review.

The operation lock remains held across one bounded overall review operation. The primary reviewer route comes only from `worker-settings.json#reviewRoute` and must be an exact authenticated `provider/model:thinking` route at `xhigh` or lower and must not select Claude Fable; there is no caller override. The same ceiling and model exclusion apply independently to the fallback route. An optional, different `reviewRateLimitFallbackRoute` must use the same exact provider. It runs at most once in a fresh child and only after the primary Anthropic route returns confirmed HTTP 429 plus `rate_limit_error`. Authentication, model/config, transport, 5xx/529, timeout, cancellation, malformed output, confinement, policy, and uncertain errors never trigger fallback. Parent cancellation remains authoritative before and during either attempt, automatic child retries and compaction are disabled, and both attempts share one overall timeout. After confirmed rate limiting and before any fallback child is constructed, a trusted callback under the same operation lock revalidates the exact handed-off lifecycle/lease, inventory/candidate/current commit, canonical confinement root, and stopped-container fingerprint (including start/finish timestamps, status, exit/OOM/error state, and restart count); timeout or cancellation prevents that callback or fallback. The same checks run again after the operation.

Each attempt uses in-memory settings, the verified `managedWorkerRoleSkillText("review")` as its exact role system prompt, no ambient/project settings or resources, and exactly repository-confined `search_many`/`read_many`. Child model copies remove Anthropic `compat.allowedFallbackModels`; the final assistant provider/model and any `responseModel` must equal the requested route. Lexical/canonical checks reject path, home, absolute, `@`, symlink, Git-admin, malformed cursor/search/glob, and unsupported-tool escapes, while native search appends Git-admin exclusion globs after caller globs so `.git` cannot be re-included; ordinary dotfiles remain available. Clean tracked worktree evidence must be single-link. Candidate diff/stat evidence is untrusted JSON string data inside runtime-random nonce boundaries, separate from the unmistakable parent-authored focus and output protocol. Candidate `.pi` settings, packages/npm commands, extensions, skills, prompts, themes, context, SYSTEM/APPEND_SYSTEM files, parent transcript, prior verdicts, worker-authored handoff prose/checks, and a partial primary transcript never enter fallback construction or prompt authority.

Trusted host Git checks bind HEAD, tree, ignored/unignored dirty state, policy, history-overlay protections, and single-link worktree evidence before and after the complete primary-plus-fallback operation. Lifecycle, container, repository, or route drift fails visibly. `worker_review` does not acknowledge completion delivery or rewrite worker records. It returns bounded structured verdict/findings/checks plus exact identity, final route, one-or-two-attempt route/outcome history, timing, and tool-count metadata. Failure messages expose ordered attempted routes and safe outcomes (`rate_limited`, `failed`, `output_failed`, `confinement_failed`, `route_mismatch`, `precondition_failed`, `timed_out`, `cancelled`, or `postcondition_failed`) but never embed raw provider errors or credentials. Timeout/cancellation aborts only the active child and releases the operation lock after postconditions; review creates no UI state, attestation, approval registry, promotion permission, or mutation/push/publication authority.

`worker_fold_prepare` is the lean `RepositoryChangeSet` boundary. Each of at most 16 mappings names one durable `candidateId`, one absolute existing local target repository below the accepted local target root (`~/Code` by default), one fully qualified existing `refs/heads/...` target, a purpose, `merge` or `squash`, and optional candidate dependencies. Before resolving candidates, the host acquires every selected worker operation lock in worker-ID order and holds the locks through publication; an active run or any lease rejects preparation, so resume/start cannot race it. Under those locks it re-reads hash-validated exact-session inventories, copies each hash-validated inventory into a mode-`0400` prepared provenance artifact and carries its relative file/hash plus bounded reported/scan-coverage evidence in the manifest, and revalidates candidate IDs, base/head/tree/dirty facts. It identifies duplicate physical targets by the `.git` device/inode pair, rejects missing/duplicate/cyclic selections, and checks target ref/tree/cleanliness/policy and linked-worktree state. Exact candidate-head and target-ref trees are rejected when they contain repository attributes or gitlinks even if the checked-out worktree differs. Dirty candidate state remains an explicit inspection fact and does not by itself invalidate an exact committed delta; tracked or nonignored untracked target changes fail closed while ignored build artifacts do not.

Preparation uses the same absolute, shell-free, callback-disabled, bounded Git boundary as inventory, additionally disabling automatic maintenance and using an empty template directory for clone/init. Temporary source bundles import reachable objects into an owner-private external view; private external refs then pin the exact expected target and candidate OIDs rather than trusting mutable `HEAD`. After target and candidate import, a bounded read-only `git fsck --strict --connectivity-only` checks the exact imported roots. Clean state and policy are checked immediately after resetting the view to the target and again after resetting it to a ready desired commit. Repository policy rejects hardlinked mutable non-object Git metadata while allowing ordinary hardlinked `.git/objects/**` content created by legitimate local clones; prepared manifests, bundles, and inventory-provenance files still require one link. Merge/squash commits use the fixed identity `Pi Worker Fold <worker-fold@localhost>`, fixed author/committer date `2000-01-01T00:00:00Z`, exact method-specific parents, and a message containing the candidate, worker/run, workspace repository, candidate head, and normalized purpose.

`worker_fold_resolve` is the explicit model-assisted path for exactly one `resolution_required` prepared repository. Start requires the exact prepared ID, manifest SHA-256, candidate ID, parent task IDs, and a bounded `IntegrationContextBundle` with decisions, rules, acceptance criteria, dependencies, rationale/checks, review evidence, invariants, non-goals, priorities, questions, author responses, and optional evidence paths contained below accepted local target roots. The host normalizes the bundle, writes hash-addressed mode-`0400` copies in trusted state and the worker artifacts directory, re-reads and verifies the immutable prepared manifest/bundle, revalidates the clean exact target ref, and provisions a new private repository at the prepared target commit. Exact candidate objects are available only through a private local branch. Trusted host Git invocations disable inherited hooks, filters, credentials, signing, external diff/merge drivers, maintenance, replace/graft overlays, commit-graph reads, and optional locks through pinned arguments/environment; these controls are not claimed as persisted repository configuration. The provisioned repository persists only the prepared bundle origin, a `/dev/null` push URL, and its private integration branch wiring. Container-side worker processes also receive `GIT_OPTIONAL_LOCKS=0`; required index/ref locks for resolution mutations remain enabled by Git.

Resolution is strictly two phase in one worker identity, Pi session, workspace, and fixed provider route. The analysis run receives immutable read-only workspace copies of context/evidence and exact target/candidate identities but must leave HEAD/tree, tracked and untracked status (including ignored files), the semantic index, refs, and repository config equal to the host snapshot. Analysis experiments and clones belong below scratch, never below `repos/`, and analysis handoff must report no repositories. Unreferenced loose or packed objects created during analysis are explicitly benign: settlement binds and rechecks the exact HEAD/tree, semantic index/status, complete refs, configuration, metadata, prepared inputs, and target rather than enumerating the full object store. This keeps validation bounded for large repositories. Its resumable handoff states are only `checkpoint` and `needs_input`; `blocked` and `failed` terminate either phase honestly and are not resumable. After the parent observes an exact resumable analysis result, a nested `request.kind:"resume"` call requires an immutable nonempty settled-decisions addendum bound to the manifest and context hashes; generic `worker_run` resume is refused. The host first revalidates context, prepared state, target state, and the pristine analysis snapshot, then validates the canonical non-symlink artifacts directory before writing decisions and permitting repository mutation. Resolution must hand off only `ready_for_review` or `assignment_complete` on success, report exactly the integration repository, produce a merge commit whose parents are exactly `[targetExpectedCommit, candidateHeadCommit]`, or a squash commit whose sole parent is exactly `[targetExpectedCommit]`, and produce a committed changed tree. The exact container is stopped before trusted filesystem/Git/inventory validation in normal completion and recovery. Target movement, artifact/context/decision/evidence tampering, repository-policy failures, wrong handoff states, extra repositories, or phase mixing fail closed.

A successful resolution handoff is inventoried as a new ordinary candidate; it does not modify or replace the prepared manifest and does not promote anything. Its inventory lineage binds the prepared ID/manifest, source candidate IDs, context and decisions hashes, analysis run, resolution worker/run/workspace identity, and exact prepared target commit/tree. Review, validation, fold preparation of that new candidate, local promotion, and publication remain separate parent-owned operations.

Integration context envelopes are bounded to 128 KiB; evidence is limited to 32 regular single-link files, 2 MiB each and 8 MiB aggregate; the trusted immutable index copy is limited to 64 MiB; prepared bundles are limited to 256 MiB and hashed with bounded streaming reads; non-object Git metadata is limited to 20,000 entries and 32 MiB; exact committed-tree listings and raw commit objects used for parent verification are parsed from owner-only no-follow temporary files and each limited to 64 MiB. Repository discovery is limited to 32 repositories, depth 12, and 20,000 traversed directories. Ordinary files do not consume traversal capacity because they cannot contain a nested repository; every nonsymlink directory still does, so nested-repository detection is not silently skipped. Exceeding a directory/depth/repository bound produces the corresponding explicit incomplete scan limitation; exceeding the exact-tree cap produces `tree_listing_output_limit`, and exceeding the raw-commit cap produces `commit_object_output_limit`; integration settlement fails closed on any such condition.

Before atomic publication, each repository gets one mode-`0400`, single-link, self-contained object bundle advertising only exact private target/candidate refs and, when ready, the exact desired ref; conflict artifacts retain the exact target and candidate objects. The manifest records artifact paths, hashes, advertised heads, prerequisites, physical target identity, dependency order, exact OIDs, repository-level overlap counts without changed-path enumeration, and bounded resolution cases. Bundle structure is verified with both `bundle verify` and `bundle list-heads` plus direct header evidence before publication and after restart. Artifact and manifest files and their containing directories are fsynced before rename. A merge conflict leaves the disposable view at the exact expected target and emits `resolution_required` without inventing a desired commit. Before and after preparation, candidate path/policy/head/base/tree/dirty facts and target `.git` physical identity, selected ref/commit/tree, and tracked/index/nonignored-untracked status are rechecked. Preparation never writes authoritative candidate or target refs, indexes, worktrees, files, remotes, or object stores; remotes and object-store contents are not claimed as before/after comparisons.

The durable reader revalidates manifest identity/hash, inventory provenance, immutable file mode/link/hash, exact bundle heads/prerequisites, candidate ID, input trees, desired tree, and merge/squash parent shape by importing the self-contained artifact into a temporary verification repository and running the same bounded read-only strict connectivity fsck over its advertised roots. Disposable views are deliberately outside manifest integrity: review or validation may modify, remove, or recreate them from the immutable artifact without invalidating the prepared record. Failed attempts remove their own unique staging directory; a process crash may leave a uniquely named `.prepare-*` directory for explicit inspection, and retry never reuses or silently replaces an existing prepared ID. Git operations are synchronous, so cancellation is checked before preparation but cannot interrupt an individual in-progress Git subprocess. This tool does not review, validate, resolve conflicts, promote, fetch remotes, push, publish, or call a model.


## Lifecycle

1. `worker_run` returns stable `workerId`, `runId`, `jobId`, `sessionId`, workspace, task, and route receipts immediately.
2. Before dispatch, the trusted host independently pins any local `initialRepos` source/revision to exact commit/tree identities without fetching or mutating the source. Nonlocal, unsupported, or unresolved sources remain explicitly unpinned. A new worker is then deferred until `turn_end` and forks the exact completed parent session with `SessionManager.forkFrom(...)`.
3. A resume verifies and reopens the exact recorded worker session. It exclusively creates a mode-`0400` completed-parent-session snapshot under the canonical, non-symlinked worker `artifacts` directory before launch; poisoned paths fail before any host write.
4. The first launch creates one exact Docker container for the worker identity, mounts all of `~/Code` read-only and only that worker's private workspace read-write at the same absolute paths, and waits for its pinned Alpine toolchain bootstrap to become ready. Successful handoffs stop that exact container to destroy its process namespace, then preserve the stopped container and writable layer for later resumptions.
5. The trusted macOS host writes its process marker, verifies an exact run/nonce/parent-PID authorization file, and only then starts Pi RPC with an explicit session file/directory, fixed model route, no built-in tools, no discovered extensions, skills, prompts, themes, or context files, and project trust forced off. Recovery revokes authorization before failed-run cleanup, fencing a host delayed before marker creation. Host-job completion remains pending until the original host process group, including its RPC descendant, has settled.
6. Pi stays alive through asynchronous shell completions and subsequent model turns until `worker_handoff` writes one accepted result and a later RPC `agent_settled` proves the handoff turn quiescent.
7. The host writes a separate trusted settlement marker only after rechecking exact session identity and quiescence. The parent accepts recovery only when both the typed handoff and matching settlement marker exist.
8. After trusted handoff settlement, the host inventories bounded physical Git repositories below the private `repos` directory without following symlinks and writes a mode-`0600`, hash-bound repository inventory under the run state directory. Each repository candidate records reported/unreported state, exact base/head/tree identities, whether committed head differs from its pinned base, one aggregate dirty flag, foldability, and bounded policy issues. Dirty state is exactly the union of tracked status with untracked reporting disabled and `git ls-files --others --directory`, so empty or ignored untracked directories remain inspection signals; it does not enumerate or count changed files. Worker-reported paths that are missing or not repositories are separate bounded issues. Scan coverage is one explicit complete/incomplete record with bounded limitation kinds rather than per-path scan noise. Host discovery is authoritative, so an otherwise valid unreported or nested repository remains eligible. A verified committed delta whose head descends from its pinned base and whose Git policy is supported is foldable even when the workspace is dirty; the parent inspects that aggregate dirty state later to decide whether uncommitted work is intentional or needs worker correction. Missing-base, no-committed-delta, unrelated-history, and unsupported-policy cases fail closed. The audited Git boundary uses one absolute executable, fixed argv, scrubbed environment, no optional locks, disabled hooks/fsmonitor/credentials/signing/editors/pagers/replace objects, bounded output, and no fetch/push. Candidate IDs bind exact worker/run/path/base/head/tree facts and change if those identities move.
9. When explicitly requested later, fold preparation resolves selected candidates from those exact inventories and writes only external immutable prepared state; authoritative targets remain unchanged. A conflict case may then use `worker_fold_resolve` for a pristine analysis checkpoint and exact-session decisions resume, producing a new lineage-bearing candidate without changing the prepared or authoritative repositories.
10. Host-side shell helpers settle normal command groups. A successful typed handoff parks the verified container in a stopped state for the same worker's next run; failed runs, cancellation, failed or uncertain crash recovery, and discard extend exact stop/kill/wait through verified removal as the authoritative cleanup boundary. Completion delivery remains pending until Pi emits the exact same-session custom `message_end` receipt for the worker/run delivery ID. Reload never scans or automatically replays ambiguous history; model-facing `worker_control result` validates and observes the exact result, while user-facing `/worker:ack` explicitly resolves a separately reviewed pending completion.

Trusted role guidance lives in package `skills/managed-worker-{parent,implementation,review,integration}/SKILL.md`. Parents discover those skills progressively. Managed worker RPC still disables ambient/project skills and adds exactly one trusted implementation or integration skill explicitly. The assignment intentionally inlines the same verified role text because this confined tool surface has no `read`/`read_many` skill loader. The packaged review role text is verified and injected directly into the dedicated settled-worker reviewer; no ambient skill discovery is enabled.

Durable state lives under `~/.local/share/agent/workers/<worker-id>/`; the private workspace lives under `~/.local/share/agent/workspaces/<worker-id>/` with `repos`, `scratch`, `cache`, `artifacts`, and `tmp` directories. Workers must clone or create every Git repository below `repos/` and report it as `repos/<name>`; handoff rejects repository paths elsewhere so inventory scope cannot silently omit them.

## Confinement and authority

Worker shell commands execute inside one Linux container per worker identity, reused across successful resumptions while that worker remains durable. `/Users/<user>/Code` is a direct read-only VirtioFS mount and the exact private worker workspace is the only read-write host mount. This intentionally gives workers read access to all files under `~/Code`, including hidden project state, while preventing writes there. Sibling workspaces, worker state, Pi/provider credentials, `BEADS_DIR`, SSH agents, keychains, host Docker sockets, and other host paths are not mounted or injected. The accepted personal-workstation policy uses Docker Desktop's default bridge and therefore permits public internet plus reachable host/private network paths such as `host.docker.internal`.

The Pi RPC/provider/Beads control plane remains trusted on macOS. Docker init owns one long-lived container supervisor shell. Each detached host helper verifies the exact container ID and worker/run/nonce labels, uses `docker exec` only to submit a host-generated launch script and observe split output, and the supervisor starts a waiting launch wrapper which owns the command's new process group. Requested cancellation targets that recorded in-container group. Container commands receive a fixed sanitized environment with caches and temporary paths redirected into the worker workspace. Canonical job IDs and metadata-owned host log paths remain independently validated.

Per-command process groups are cooperative convenience, not the final containment primitive. Every terminal run first settles host helpers and then stops, kills when necessary, waits for, and verifies the exact labeled container, so a descendant that calls `setsid()` or clears its environment still disappears with the container PID namespace. A successful normal or crash-recovered handoff retains only that verified stopped container; failed or uncertain recovery and all other terminal paths remove it. The run remains active and leased if either shell or container cleanup cannot be verified.

The Pi RPC host remains trusted and outside the shell sandbox so it can use the configured provider route and central Beads store. `worker_task_read` uses Beads 1.1's official `bd --readonly search` and `bd --readonly show --include-dependents --json` paths after exact route verification. Workers can page their assigned roots, search all central tasks by title or ID, and read up to four arbitrary central task IDs per call. Every returned task and relationship marks whether its ID is assigned to that worker. Task text, direct dependency/dependent summaries, search results, raw CLI output, and provider-visible content remain bounded. The worker container receives no `bd` binary, database mount, route path, or `BEADS_DIR`, and the adapter exposes no arbitrary Beads command surface.

Beads mutation remains available only through `worker_task_update`, which:

- accepts only parent-assigned task IDs;
- verifies `bd where --json` matches the exact parent-recorded central `personal` path and database, with the unchanged ambient `BEADS_DIR`, before each access;
- appends notes and may set only `in_progress` or `blocked`;
- cannot close tasks or mutate arbitrary IDs.

Workspace `.pi/settings.json`, extensions, skills, prompts, themes, `SYSTEM.md`, and `APPEND_SYSTEM.md` are not trusted or loaded. Explicit trusted worker runtime extensions are the only exception.

## Handoff and cancellation

`worker_handoff` accepts `ready_for_review`, `assignment_complete`, `needs_input`, `blocked`, `checkpoint`, `failed`, or `cancelled`, with summary, task updates, optional repositories/checks, and optional question. Before calling it, the worker must inspect every owned async-shell job, choose to wait for work that should finish or cancel work that should stop, and verify terminal status. Handoff admission seals new shell starts, checks both the live registry and persisted job/process-token state, rejects every active or unverifiable job, and rejects duplicate handoffs. Once accepted, `shell_start`, `worker_task_read`, and `worker_task_update` remain sealed; the host independently rechecks RPC and actual process-group quiescence before settlement.

`/worker:view` opens the existing bounded, provider-free async-shell TUI for the worker's active or last host run. `/worker:ack` explicitly acknowledges a settled pending completion after inspection; automatic delivery acknowledgment comes only from the exact same-session custom-message receipt. Parent models use `worker_control result` instead of blind acknowledgment. `/worker:cancel` and `worker_control cancel` remove queued runs before launch; cancelling a queued resume also removes its previously parked container, retaining recovery ownership if that removal cannot be verified. Running host and command process groups receive bounded `SIGTERM` grace followed by `SIGKILL` escalation when necessary, after which the exact Docker container receives explicit `SIGTERM`/four-second stop and verified removal. Detached host cancellation still requires a matching trusted process marker and host command identity. Discard requires explicit confirmation, refuses active workers, removes the parked container when present, removes the private workspace, and removes durable state last.

An exclusive per-worker run lease prevents concurrent resumes. Cancellation records an exact durable cleanup owner before any host/container mutation, so normal completion cannot park/release the same run or expose its container to resume concurrently. Recovery atomically clears a cleanup owner only while replacing its dead parent lease. Host settlement is proven independently from recorded process-group liveness rather than inferred from identity-verification failure. Short record/lease transitions are additionally serialized by a trusted per-worker claim-directory operation lock; dead-owner claims are pruned and concurrent reclaimers elect exactly one owner. Launch revalidates the exact queued record and lease immediately before spawning. Resolution rollback releases its resolution lease before atomically restoring the older analysis record, so a crash leaves an explicit queued lease-free run that restart recovery can claim and finish rather than a completed record with a mismatched lease. A trusted host-process marker closes the spawn-before-parent-PID crash window and supports exact restart adoption; stale PID data alone never authorizes signaling. If cleanup cannot prove owned shells are gone, the run and lease remain active with a visible recovery error; a later verified sweep can finalize cancellation instead of making the worker resumable prematurely.

## Setup and limitations

- Requires Node 22.19 or newer, macOS, a running Docker Desktop/Engine with the Docker CLI on trusted parent `PATH`, and local arm64 image `alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce`. Pull it explicitly with `docker pull --platform linux/arm64 alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce` before starting workers; launch fails loudly when it is absent.
- Requires `bd` on trusted parent `PATH` and an ambient central `personal` route for task updates.
- Requires `worker-settings.json` with a valid `defaultRoute` such as `provider/model:thinking`; subagent routes reject `max` and Claude Fable. The profile or package config supplies the default; `worker_run.runs[].route` remains the per-new-worker override.
- This vertical slice bounds each `worker_run` batch to eight but does not yet implement the later configurable cross-run concurrency scheduler or its 1–4 benchmark.
- This slice derives durable repository-level candidates, implements nonauthoritative `worker_fold_prepare`, and provides explicit two-phase `worker_fold_resolve` for prepared conflicts. Review/validation binding and local exact-ref promotion remain separate later capabilities; neither a handoff, candidate, prepared artifact, nor resolved candidate authorizes promotion.
- Publication, installation, provider trials, and promotion remain normal parent-owned reviewed operations.
- The exact stopped container persists across successful handoffs and restarts for resume, so container-root package changes and workspace caches remain available to that worker without allowing background processes to survive between runs. Failed/cancelled runs, failed or uncertain crash recovery, and discard remove it; a successfully recovered handoff may preserve the verified stopped container, and a later permitted resume otherwise creates a fresh replacement.
- The pinned Alpine bootstrap installs a broad Node/Python/build/Git shell toolchain at run start. ARM64 Linux cannot run Xcode, Darwin binaries, or macOS-only validation; those remain parent-owned checks.
- Command-level cancellation remains cooperative for descendants that leave their process group. Whole-container removal is authoritative run cleanup and handles those descendants independently of PID, process group, or environment tokens.
