# worker

## Purpose

Managed-worker v2 provides durable, resumable work, independent review, conflict integration, and exact local merge preparation/application. The parent remains responsible for scope, grounding, acceptance, validation, publication, and task closure.

## Tools

Parent tools:

- `worker_run`: start `work`, `review`, or `integration` roles, or resume an exact worker.
- `worker_control`: `list`, `runs`, `get`, `cancel`, narrow same-session `discard`, `cleanup_inventory`, `cleanup_preview`, `cleanup_apply`, and `preserve`.
- `worker_merge_test`: create a fresh isolated prepared set from explicit candidates and exact targets.
- `worker_merge_apply`: apply one ready parent-validated set after global preflight.

Worker-only tools:

- `worker_result_submit`: submit one role-valid outcome, concise summary/question, and canonical workspace repository/artifact paths; the runtime seals and reconciles owned work internally.
- `worker_beads_tasks`: bounded assigned/get/search reads, digest-fenced UTF-8-byte continuation of canonical `design` fields, and assigned-only work/integration progress updates. Every inline and continuation view includes lowercase SHA-256 of the complete canonical UTF-8 design plus `totalBytes`, `returnedBytes`, `truncated`, and `nextOffset`; continuation requires that digest and rejects task revisions with a restart-at-zero error. Every provider-visible read remains within 64 KiB. Search omits design content, reviewers retain read-only access, and no branch can close tasks or change dependencies.

Human commands are `/worker:list [status] [role]`, `/worker:show <workerId> [runId]`, `/worker:view <workerId> [runId]`, `/worker:logs <workerId> [runId]`, `/worker:cancel <workerId>`, `/worker:discard <workerId> --confirm`, and `/worker:cleanup [--all-sessions] [--offset N] [--cursor <token>] [--confirm <token>]`. `/worker:view` opens a bounded, read-only manual-refresh rendering of the exact retained run range. It uses bounded transcript pages rather than refusing long runs: `[`/`]` move between pages, `J`/`K` jump between block boundaries, `g`/Home unambiguously opens the first run page, `G`/End opens the latest, and `r` refreshes the latest registry-backed snapshot. Compaction visibility follows Pi's exact `firstKeptEntryId` boundary across the run before pages are selected, so both traversal directions expose the same chronological set. A boundary before the retained run hides none of that run; otherwise the opening assignment remains reachable and a bounded warning counts only truly superseded entries. Pages obey a 512-entry limit, a 7 MiB decoded-content target, a separate 7 MiB encoded-entry display bound, and a 2,048-rendered-block limit; the byte bounds preserve 1 MiB of headroom beneath the hard 8 MiB total-I/O ceiling. Entries reaching or exceeding the 7 MiB display bound are prefix/index-classified, skipped, and reported rather than risking a non-progressing page. Page selection advances atomically past a whole boundary entry even when its physical line exceeds the byte target; fully consumed block-cursor entries do not spend the next page's byte budget, and adjacent multi-MiB entries remain reachable in both directions. Earlier/later counts include only entries that the viewer actually displays. Rank/select chooses a displayable materialization anchor before page I/O, so hidden, malformed, and skipped oversized spans cannot produce an intermediate empty page or advance a cursor past an unread display; terminal empty ranges remain terminal. Malformed and oversized records skipped between anchors are attributed to exactly one reachable page, and backward terminal pages report oversized records skipped before their first displayed entry without moving the page cursor. Run line indexes are streamed, fingerprint-validated, and reused, with sampled byte checkpoints plus exact pinned start/end spans for every multi-MiB and oversized line. Compact per-run display, oversized, and malformed bitsets with 256-line cumulative ranks provide exact compaction-adjusted counts and select visible anchors without budgeted historical rescans; bounded head/tail identity metadata resolves oversized Pi custom first-kept targets. Rank-selected lines materialize directly through one request-local no-follow range cache, pinned nondisplay spans are skipped by exact offsets without rereading payloads, and only small unpinned gaps scan within the remaining budget. Bounded 256 KiB read-ahead retains header/fingerprint headroom while fitting normal page I/O within 8 MiB by stopping at complete progress boundaries rather than surfacing a read-budget error; cached oversized spans preserve exact notices without rereading payloads. Every async open extends a private line-index and visibility view frozen to its file size, and promotes immutable cache copies only by a newer-generation/size CAS, so settlement counts, synchronous readers, and concurrent refreshes cannot move its boundary. Running refresh extends only a stable appended suffix, running state promotes incrementally to a later settled boundary, and settled views stop indexing at their retained end. An unterminated final line is indexed once per opened snapshot, yields before returning, and is retained as bounded running-state evidence for a later append; a settled snapshot reuses that decision only at the identical file size, so growth is rechecked before a completed final entry can be excluded, while a still-partial settled snapshot shows an explicit notice. Empty settled ranges render normally, and interactive cold scans yield between bounded chunks. Malformed ranks preserve exact notice accounting even when a pinned malformed payload is skipped during page materialization. Rendering has per-block and per-page character/line budgets before wrapping, so adversarial pages cannot monopolize input. Transient line-count snapshot races receive bounded retries through one no-follow descriptor and original file identity, while replacement fails with a stable error instead of counting a new path or leaking an internal empty-message exception. The command never acknowledges delivery or mutates worker lifecycle state.

## Identities and registry

A `workerId` is reusable. Every execution has an immutable `runId`; task/model snapshots, logs, session ranges, result, repositories, artifacts, errors, and timestamps belong to that run. Pre-host launch diagnostics use best-effort files inside the run directory, never the future async-shell job directory; successful launch atomically replaces those paths with the published host logs. Every launch, settlement, and cancellation claim nonce is bound to an owner PID/start-token digest and has a matching durable admission record, closing the claim-to-file publication gap. Parent runtime registration, foreign-owner liveness evaluation, and interrupted-claim recovery share one write transaction; claim acquisition is fenced to the current generation. Fresh extension instances preserve a live operation token and recover only dead owners. Pre-host launches persist immutable project/session inputs before deferral and never retain an `ExtensionContext` across reload or session replacement. Same-run recovery parks and verifies any exact existing execution containment before restart; launch-side mutations check the exact registry claim before and after each effect, retain and cancel a started handle if a post-effect check fails, and unauthorized failure paths never remove an adopted resource. Resume validates retained-session identity through a bounded no-follow header read with session-directory path-component containment and derives the next run start from the previous run's committed end boundary. Settlement line counts and viewer pages use bounded-memory no-follow leaf-file reads with stable file-identity checks; they do not claim the stronger path-component containment used by header verification. Resume therefore performs no size-dependent JSONL scan or materialization, including for sessions beyond Node's maximum string length; settlement line counting remains streamed and bounded-memory.

Trusted host processes open one owner-only SQLite database at `~/.local/share/agent/worker-runtime/registry.sqlite`. SQLite transactions serialize lifecycle changes. Numbered schema migrations run transactionally; schema-source fingerprints are diagnostic rather than an availability gate. Each worker has one guarded parent: `worker-runtime/workers/<workerId>/guest/` holds durable guest-writable sessions, workspaces, repositories, artifacts, caches, async state, and validated run inputs, while sibling `host/` holds supervision and trusted evidence and is never mounted into the Sandbox. Deletion claims stay in the registry outside the recursively deleted worker parent. v2 does not import or silently move legacy worker/fold state.

Completion settlement inserts a stable delivery record in the same transaction. The newest runtime generation for the exact parent session claims pending delivery; `PRAGMA data_version` plus an unreferenced one-second check makes delivery durable. Claiming and starting the send are separate persisted boundaries. Promotion CAS-releases only a provably dead runtime's pre-send claim for automatic delivery; once `sendMessage` starts, absent session evidence is surfaced with its exact run ID as `send_started_unconfirmed` in worker list/get and `/worker:list`/`/worker:show`, and is never automatically replayed because acceptance is ambiguous. At `agent_end`, exact same-session history may acknowledge that delivery as delivered; this receipt-only reconciliation never sends, replays, or steers the model. Startup or runtime promotion emits one UI-only warning per exact unconfirmed run and runtime generation; it never steers the model or changes worker counts. Delivery state is transport bookkeeping and never gates resume. The compact TUI footer derives `wN` from exact-current-session queued/running registry rows and updates on committed registry transitions; direct visible async-shell work remains the separate `shN` count. Both disappear at zero. Separately, collapsed worker call/progress/result rows show a width-bounded operation hint derived only from complete structured call arguments, trusted returned details, or bounded in-memory snapshots captured as a byproduct of authoritative preflight reads. Rendering performs no filesystem, process, Beads, or registry I/O; unavailable context and optional titles are omitted. Worker prose and artifact contents never enter the hint.

## Package generation safety

Worker registration hashes only the checked-in, packaged worker-runtime files named by `extensions/_shared/package-generation-files.json` and records their exact file identities in process-global state. Later tool, deferred launch, reconciliation, cancellation, and discard boundaries first compare cheap metadata stamps and rehash only after a listed file or the manifest changes. Checked-in exact normalized-source fingerprints exported by the actually cached plain-JavaScript `async-job-process`, `atomic-json`, and `worker-job-settlement` modules catch the first old-process/new-disk transition before a missing export can be called; normalization replaces only the fingerprint literal itself so TypeScript test emission preserves the marker. Default configuration and unrelated untracked development files are outside this executable manifest. A mismatch notice is process-local and never replaces durable per-run recovery state; after a clean restart passes the guard, normal host supervision resumes. Package installation or update requires fully quitting and restarting Pi: `/reload` remains supported for same-generation worker delivery and context/configuration changes, but it is not a package-code activation mechanism.

## Roles and results

`work` and `integration` may submit `completed`, `needs_input`, or `blocked`. `review` may submit `approve`, `request_changes`, `needs_input`, or `blocked`; approve/request-changes requires a retained detailed report artifact. Only the worker system creates `failed` or `cancelled`. Semantic rejection returns coded field errors without sealing. Every accepted result records `outcomeSource` as `worker` or `system`.

Role instructions are verified regular UTF-8 files under `worker-roles/`. Ambient/project skill discovery remains disabled. The package exposes only `skills/managed-worker-parent/SKILL.md` to parents.

Repository paths must identify contained Git repositories. Artifact paths may identify contained regular files or directories. Work-start repository baselines are parent-validated provenance only: their exact paths and commits are recorded in the prompt but are not mounted and may be unreachable from the worker. These are live workspace pointers, not immutable artifact snapshots. Reviews therefore start only for the latest completed idle subject run.

## Review

Only a latest idle work/integration run with worker-submitted outcome `completed` is review-ready. Worker-submitted `needs_input` and `blocked`, and system-settled `failed` and `cancelled`, are not review signals. Review launch chooses the first available configured review selection whose provider differs from the subject provider and fails before launch when no independent provider is available.

The parent launches a review for every eligible completed result and treats its outcome as advisory evidence. On `request_changes`, the parent resumes the same subject worker with the findings and reviews its next completed run; the default parent-driven workflow stops after that one correction/re-review cycle unless the parent deliberately authorizes another. Review never accepts, applies, publishes, grounds, or closes tasks.

A reviewer has its own retained writable worker root and one fresh writable disposable OverlayFS view of the complete subject workspace. The host-validated subject is mounted read-only as the lower layer; `sbx exec --user root --privileged` mounts private in-Sandbox upper/work directories at `/review/subject`, and Pi runs there directly for tests, builds, edits, and experiments without a full subject copy. The exact Sandbox owns and removes upper/work/merged state on every terminal path. The unprivileged Sandbox RPC shim revalidates the exact lower/upper/work OverlayFS mount options immediately before it execs Pi, so a restarted Sandbox cannot launch a reviewer into an empty mountpoint. Bounded session/context evidence and additional inputs remain read-only; retained reports belong in the reviewer workspace, and neither lower subject bytes nor authoritative repositories can be mutated. The reviewed worker is leased against resume while review runs. Review workers have proxy-mediated provider access but no task mutation, fix implementation, push, target mutation, application, publication, or acceptance authority.

Every run, including resume, gets a newly created Docker Sandbox from the latest approved immutable image/kit manifest. Only the exact `guest/` child is mounted read-write; validated run inputs beneath it and explicit external inputs are mounted read-only, and sibling `host/` is never mounted. The host loads executable extensions only from immutable manifest-approved image paths with project discovery disabled; guest-writable extensions and prior agent configuration are ignored. Host-authoritative claims, authorization/revocation, launch configuration, process identity, accepted result, settlement evidence, and delivery remain host-only.

## Merge testing and application

`worker_merge_test` accepts 1–16 request-local IDs, local candidate repositories and optional exact refs (default `HEAD`), target repositories/branch refs, merge or squash methods, commit messages, and a request-local dependency DAG. It resolves exact commits and creates ordinary isolated prepared repositories containing target and candidate history. Ready repositories contain exact commits; conflicts retain ordinary Git index/worktree state.

The tool never mutates targets. Managed and historical candidates are discovered by path and exact commit and produce advisory provenance warnings; arbitrary local Git candidates and parent-resolved prepared repositories are also accepted. Every call creates a new `preparedId`. Any target movement requires a fresh test. A complete conflicted set can be atomically moved into one integration worker workspace, consuming that prepared set.

Prepared-set lifecycle and repository records in the SQLite registry are authoritative. `prepared.json` is a rendered inspection/context artifact only; integration and apply never trust worker-writable copies as authority.

After parent review and validation, `worker_merge_apply({preparedId})` globally preflights every exact clean target. It then applies dependency order using `git merge --ff-only` for checked-out refs or compare-and-swap `git update-ref --no-deref` otherwise. Earlier updates remain after a later operational failure; retrying the same prepared ID skips exact already-applied commits.

Trusted Git disables hooks, signing, credentials, global/system configuration, replace/graft overlays, and hostile merge configuration; linked candidate worktrees, per-worktree configuration, and gitlinks/submodules are rejected. Ignored or untracked nested repositories are inert for trusted-Git policy validation. Apply cleanliness is separate: an ignored nested repository remains clean, while an untracked nested repository makes the exact worktree that checks out the target ref dirty. Refs not checked out anywhere are compare-and-swap updated without inspecting an unrelated worktree; active target refs checked out in another worktree are updated through that exact clean worktree. Application performs no model call, conflict resolution, testing, push, release, grounding, or Beads mutation.

## Typed review completion

Review verdicts are authoritative only through `worker_result_submit`; unstructured assistant prose is never promoted into a result. If a review turn becomes fully quiescent without a typed result, the supervisor waits the normal five-second protocol grace and injects one bounded repair turn that requires the existing typed tool and retained report artifact. A second quiescent turn without a valid submission fails closed. Initial, asynchronous-follow-up, and repair prompts inspect Pi's correlated RPC response directly so `success:false` causes are retained instead of becoming a generic prompt-start watchdog failure. Injected prompts request follow-up streaming behavior; a busy rejection is benign only when authoritative RPC state shows an active turn, otherwise the same one logical opportunity is retried once without resetting the one-shot flag.

## Cancellation and retention

Cancellation requests and failed pre-host cleanup first persist owner-independent terminal intent. A cancel from an older same-session runtime is still accepted atomically; it reports `accepted_pending` while the newest live runtime owns lifecycle side effects, or `superseded` if another terminal result won the atomic race. If the newest runtime exits, the latest remaining live runtime is elected by process/start-token proof and a registry CAS before it may reclaim queued or terminal-intent work. The current/elected runtime also probes every exact lifecycle claim at the bounded reconciliation interval; only a provably dead PID/start-token owner is CAS-released, after which queued launch or running settlement reconciliation continues immediately. Verified accepted result evidence always takes precedence over a later cancellation request and is settled/delivered with its recorded outcome. If this runtime still has the exact attached host, cancellation returns `superseded` immediately and leaves normal handle completion to perform the sole containment and settlement. Superseded runtimes cannot start workers or claim lifecycle side effects without that promotion. Reconciliation never clears that intent or relaunches the run; any current or successor instance may claim it only to retry exact containment through finalization. Every terminal path first waits for any live durable lifecycle owner, revokes run authority, and drains admitted mutations, asks the exact supervisor to close Sandbox RPC stdin and wait boundedly, then stops/removes and verifies the exact Sandbox even if host-process identity is ambiguous, and proves the exact supervisor process group absent. Result submission and Beads mutation recheck durable authorization immediately before mutation. Host-side job records are reconciled afterward. Supervisor liveness and signalling require both the persisted OS start token and a unique command-environment token; permission-ambiguous PIDs still have their start token compared. A stale/reused PID is dead; a matching token remains recovery-required only when ownership enumeration itself is unavailable, while a completed readable scan without the exact token proves dead. SIGKILL is checked and followed by absence probes. Any authorization, drain, Sandbox, signal, liveness, or proof uncertainty retains terminal intent and recovery authority indefinitely; it never becomes launchable, ages into `failed`/idle, or permits overlapping resume. Waiting behind a provably live owner is pending work rather than a recovery error, and healthy finalization clears transient recovery evidence. The parent process start token is cached once; foreign-owner checks are interval-bounded and unreadable identity remains fail-closed. Only deterministic post-containment settlement failures use the bounded three-attempt system-failure path, retaining accepted results and scoped evidence.

Managed-worker package/schema upgrades require restarting **all** Pi processes that share the registry. Schema v10 records the guarded common-parent storage generation and marks every schema-v9 worker recovery-required rather than silently moving or adopting legacy split state; schema v9 added identity-bound cleanup-leftover claims; schema v8 added one-use filesystem scan cursors and leftover observations; schema v7 added host-only one-use cleanup snapshots; schema v6 added cleanup preservation records and prepared-set task lineage; schema v5 added the durable completion-send boundary and conservatively retains legacy v4 claimed deliveries as send-unconfirmed; schema v4 added durable terminal intent (including migration of an interrupted v3 cancellation claim). Older processes reject newer schemas rather than operating with mixed lifecycle semantics. Session-end line capture is bounded and best-effort in every finalization path: missing, unreadable, replaced, or truncated session files become sanitized run evidence rather than an escaping retry rejection or parent-process crash.

Cancellation preserves workspace/session/evidence. Resume after cancellation includes a warning to inspect interrupted Git operations and never removes locks automatically. `discard` is idle-only, permanent, and never auto-cancels. There is no automatic garbage collection.

## Configuration

```json
{
  "modelPreferences": {
    "work": ["openai-codex/gpt-5.6-sol:xhigh", "anthropic/claude-opus-5-5:xhigh"],
    "review": ["anthropic/claude-opus-5-5:xhigh", "openai-codex/gpt-5.6-sol:xhigh"],
```

Fallback is startup-only before worker-visible effects. An explicit work `modelSelection` disables fallback. No package-imposed worker deadline exists.

## Repository discovery boundaries

Repository discovery prioritizes `workspace/repos/`, schedules ordinary top-level roots ahead of broad `artifacts/`, and protects direct reported repositories from unrelated breadth. Runtime-owned `workspace/cache/` and `workspace/tmp/` are intentionally excluded, as are recognized HOME tool-cache subtrees such as Cargo registries, verified Python environments, package stores, and build caches. Inventory limitations explicitly name each policy-pruned tool-cache subtree and aggregate breadth exhaustion by broad subtree, rather than silently hiding the boundary. A directory merely named `venv` is not pruned unless it contains `pyvenv.cfg`, and `.local/share` is not excluded wholesale. Keep candidate repositories under `repos/` (or another ordinary workspace directory); a reported repository inside an excluded cache/temp subtree fails closed as not independently found.

## Beads-derived cleanup and artifact preservation

Cleanup eligibility is derived on demand from the authoritative registry and current central `personal` Beads facts; relevance and cleanup-due state are never persisted. Workers classify in fail-closed order as active, recovery-required, undelivered, task-missing, Beads-unavailable, retained, due, or leased. A worker is due only when every assigned task is closed. Prepared sets retain inherited task IDs and classify as due, retained, explicit-decision, partial, claimed, or discarding. Beads-unavailable state by itself never triggers a model turn.

`worker_control({action:"cleanup_inventory",allSessions?,limit?,offset?,cursor?})` is bounded and read-only. It scans bounded 64 KiB head and tail windows for real `session_info` records, applies empty-name clearing, uses a tail update as latest, and reports `truncated` when an unread middle prevents a global latest-name claim. All-session filesystem accounting binds a streaming numeric position to each root's identity and name-change metadata. Each page asynchronously replays prior raw names without rereading their metadata, then applies an independent 5,000-candidate/10-second new-accounting bound; a partial result returns a persisted one-use `nextCursor`, so roots above 200,000 names remain eventually reachable without rereading prior `meta.json`. Historical worker roots, discard trash, prepared roots, and exact worker-host logs are paged. An interrupted `.cleanup-*` directory is eligible only when a host-only registry claim outside the deleted tree binds its root, source kind/ID/path, actual entry name, nonce, device, and inode; the claim is committed before rename and deleted only after the tree. None is removed automatically or by ordinary async-shell pruning.

Mutation is a two-step host-authority protocol. `cleanup_preview` accepts exact bounded worker, prepared-set, and leftover IDs, expands review lease closure, and persists one host-only one-use token. The snapshot binds every worker version/latest run/owner, exact delivery ID/state/runtime generation/run/outcome/bounded summary, task facts, artifact gaps, claims, lease state, prepared status/apply nonce, owner-runtime evidence, and leftover filesystem identity. `cleanup_apply` directly revalidates each selected leftover once without rescanning whole roots, revalidates the other bound evidence without creating a replacement snapshot, and consumes the exact token once. It requires exact per-worker lists for open-task abandonment, artifact loss, foreign pending/claimed-delivery takeover, and recovery retry. Missing or unavailable task facts, active/claimed or irreversible recovery state, live or ambiguous foreign owners, and changed evidence fail closed. A foreign pre-commit recovery row may be adopted only with exact recovery acknowledgement and exact bound recovery/version/run/operation facts when its owner is dead, retired, or missing. Stale snapshots and changed-root cursors are invalidated; consumed control rows and old observations are deterministically bounded without deleting logical workers. The tool is context-reviewed high-risk; the slash command still requires explicit human `--confirm`.

Any current-session non-delivered result is ineligible and must settle through normal delivery recovery. A foreign pending or claimed delivery can be taken over only under its exact acknowledgement and only when the prior owner is dead, retired, or missing; the database CAS binds delivery ID, state, runtime generation, worker version, and the previewed evidence, so a later original-owner CAS loses safely. Reviewers and subjects are one authority unit: preview co-selects them, adoption is atomic, the reviewer is discarded first, and the subject is freshly reread and claimed only after lease release. A per-item failure does not abort later items. Once adoption/takeover/claim begins for a reviewer/subject unit, every unprocessed member remains with the adopter with exact recovery and consent facts; a pair is released only when no member was attempted. An attempted pre-commit failure remains retryable through a new preview plus `recoveryAcknowledged`. Fresh-generation recovery preserves that adopter ownership and retry path; the returned tool result marks any partial failure as an error and names each failed ID.

Direct `discard` remains deliberately narrow: same-session, idle, no recovery or run claim, every delivery already delivered, every task closed, and exact artifact-loss acknowledgement where needed. It directs any early loss or delivery takeover to preview/apply. Discard first plans exact host-log identities without deletion, then claims the worker and atomically renames the complete per-worker parent to discard trash. Only after that irreversible boundary does it delete identity-validated external logs/prepared state, any explicit legacy external supervision, the claimed parent, and finally the registry authority row. Never-launched pseudo logs are skipped, exact absent logs are complete, and live or liveness-ambiguous logs retain recovery authority. Startup finishes committed interrupted worker and prepared-set discards. Logical workers, sessions, runs, evidence, repositories, and artifacts otherwise remain indefinitely until explicit guarded discard.

After the first `agent_end` in a runtime generation, one paged, explicitly partial other-session aggregate may be sent even when the current session owns no workers. Its dedupe key is the exact parent session plus runtime generation, so equal generation numbers after a session switch cannot suppress it. It is not reannounced on current-session churn. Current-session notices remain advisory and transition-deduplicated, include lease ordering, and never delete state.

`worker_control({action:"preserve",workerId,destination,paths?})` publishes selected ordinary artifacts outside managed/sensitive storage. Source traversal is asynchronous and no-follow component by component, rejects symlink ancestors, repositories, nested `.git`, and special files, and rechecks device/inode and file size around verified copies. Destination and forbidden roots are canonicalized with universal ASCII case-folded containment and every existing destination ancestor is compared by device/inode with every existing forbidden root, covering second mounts, firmlinks, case aliases, and normalization aliases. Symlinked nearest existing ancestors are realpath-resolved; symlink ancestors in the final destination, every case-folded `.pi` component (including project `.pi/extensions`), and resolved `.git` components are refused. Publication uses a recoverable exclusive sibling lock, a bounded sibling temporary tree, byte verification, and atomic no-overwrite publication. Coverage is host-recorded and applies only to the unchanged latest run.

Workers should remove temporary clones, reproducible build/test environments, caches, and disposable debris before result submission. They should retain clean committed candidate repositories, required reports, declared non-reproducible artifacts, and exact review/resume evidence. Artifact paths must be workspace-contained ordinary files/directories and must not themselves be standalone, shallow, nested, worktree, or bare Git roots; ordinary subdirectories inside a repository remain valid artifact entry points. Completed review results require a non-empty ordinary report file artifact.
